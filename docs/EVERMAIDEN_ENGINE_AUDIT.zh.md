## 格式与处理规则

### 1. 漏识别 Vorbis mode 3 WAV

音频格式样本为 `wav.xfl/2559.wav`。
它与已支持的压缩 WAV 一样，在 66 字节封装后直接存放 OGG，
但格式标签是 `0x6751`，不是 `0x6771`。
这两个标签分别对应 Vorbis mode 3 / mode 3 plus，参见
[VLC 的音频格式标签定义](https://github.com/videolan/vlc/blob/master/include/vlc_codecs.h)。

样本具体结构：`fmt` 长度 26、扩展长度 8、双声道 44100 Hz、
`fact` 样本数 843757、`data` 长度 250668；`OggS` 从偏移 66 开始。

修复保留原有头部、OGG 页和参数检查，只额外接受这个已验证的标签。
回写保留模板的格式标签和编解码扩展字节，并按 OGG 重建长度、样本数和补齐字节。
没有顺便放行其他未验证的 Vorbis WAV 模式。

### 2. 漏识别优化后的禁则表

旧实现只识别直接 `CMP SI, imm16` 的机器码。
本 EXE 的两张表使用 `MOV EAX, imm32 / CMP SI, AX / JE`，
前 38 项为行首禁则，后 12 项为行尾禁则；内容仍是 CP932 日文表。

- 第一张表从 `0x457961` 开始；后接 `0x213f`、`0x3f21` 和 `CMP SI, BX`
  三项扩展规则，行尾表从 `0x457b9a` 开始。
  `0x45786b–0x457875` 将 BX 设为 `0x2121`。
- 第二张表从 `0x45d248` 开始，不含这三项扩展；行尾表从 `0x45d45c` 开始。
- 第一张行尾表前两次 JE 为近跳转，第二张只有第一次；其余为短跳转。
- 第一张表分别跳至 `0x457c54` / `0x457c37`，第二张跳至
  `0x45d508` / `0x45d4f0`，将字符标为行首禁则或行尾禁则。

新增识别要求完整匹配已知字符序列、零扩展常量、比较指令和 JE 结构。
只改写 50 个字符操作数，ASCII 前缀、扩展规则、指令和跳转全部保留。
字体 charset 已经是 GBK 时也仍检查 CP932 表，避免把部分汉化误当成全部转换完毕。

### 3. 漏识别夹入指令的字体参数

`0x46d738`、`0x46da28`、`0x46e4eb` 三处 `CreateFontA` charset
仍为 `0x80`，与另外 10 处的 `0x86` 混用。
这些调用在参数压栈之间插入了函数指针载入和字重计算，旧的连续字节匹配跳过它们。
例如 `0x46e4df` 从 `0x4c8024` 载入 `CreateFontA`，`0x46e507` 调用 ESI。

新增规则匹配完整的已观察调用形状，而非任意 `PUSH 0x80`；只替换 charset 操作数。

## 其他处理路径

- WCG：`0x478150` 检查头；`0x4781ff` 按版本分派；
  `0x478222` / `0x478233` 处理配对通道；`0x478244` 先解 A，
  `0x478250` 检查是否还有 RGB，与现有实现一致。
- 调色板：`0x47b84d–0x47b85b` 的 4096 项分界、`0x47a700` 起的索引读取
  与此前修复一致。该次分析实际 WCG 都是 `0x0271`，不能据此称其他布局全部实测通过。
- LIM：`0x4786df` 的版本分派与已核对的 CannonBall 路径一致；该次分析没有实际 LIM 样本。
- XFL：`0x47629b–0x4762f8` 使用 `lstrcmpiA` 二分查找；现有 ASCII 大小写折叠字典序
  与该路径一致，仍不保证任意非 ASCII 文件名等价于 Windows NLS 排序。
- GSC：`0x404faf` 附近加载脚本，`0x405458` 序列化时计入 36 字节头。

## 尚存限制

引擎的 `IsDBCSLeadByteEx` 仍使用 `CP_ACP`，例如 `0x44dc33–0x44dc35`。
字体 charset 和禁则表转换**不会设置系统代码页**，需要匹配的 Windows 区域设置或
Locale Emulator。跨系统代码页自动运行需要进一步核对字符读取和系统 API 路径，
不能只替换字体参数，也不能盲目修改所有 `PUSH 0`。

原游戏中的画面、实际禁则效果、音频播放及真实 Windows 验收仍由使用者完成。

## 官方日文程序的 GSC 加载与执行核对

本节独立分析官方 `Evermaiden/startup_jp.exe`，
SHA-256 `88820f28b8f770b486407e55dda28266c6fec42145192d5bc8ad5be21ab895af`。
PE32，映像基址 `0x400000`；以下为虚拟地址，未运行或修改程序。

| 路径 | 二进制证据 | 修复 |
| --- | --- | --- |
| GSC 加载 | `0x404ee0–0x40526a` 读取 9 个头字；代码、字符串索引/正文、数据索引/16 位字区之后，`0x4051ab–0x4051dd` 依次读取两张各 `header[7]` 字节的表和 `header[8]` 字节的名字区 | 明确尾部是运行时命名入口，不能仅视为调试表 |
| 命名入口 | `0x404e00–0x404e51` 跳过槽 0，按第一张表的名字偏移匹配，再返回第二张表的代码偏移；`*jump` 经 `0x43df90` 使用该入口 | 导出入口标签，TSC 增删指令后重定位尾表；缺标签报错，不沿用旧地址 |
| 局部调用 | opcode 200 的 `0x43613a–0x4361ab` 读取 D 地址及十个表达式，保存返回位置；`0x43dea0` 调 `0x405760`，后者拒绝地址 ≥ 代码大小，并设置代码起点加地址 | `*insub` 首参数改为标签，校验边界并随正文重定位 |
| 数据块 | `0x4361f3` → `0x43d4e0` → `0x404d50`；零编号直接返回，非零经索引表定位；`0x404d6e` 的 `MOVSX` 将数量按 signed int16 扩展后用于复制 | 拒绝超限数量、越界块引用；允许零编号不复制的情况 |

实际日文 `0001.gsc` 有 `TOP1` / `click` / `TOP2` 入口，代码地址分别为
`0xa6` / `0x25c` / `0x7da`；`2190.gsc` 的 `REP002` 位于 `0xd9c`。
无修改往返不能暴露此问题：只有编辑入口前的指令长度，才会让原样复制的地址失效。
现在名字区、槽 0 和额外填充仍保留，不新增整段代码/字符串备份。
旧版导出的非空入口 TSC 或数字 `insub` 参数应重新导出。

非 ASCII 入口名的跨代码页转码、未知 opcode 语义和原游戏路线验收不在分析时证据范围内。
